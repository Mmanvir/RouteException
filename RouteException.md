# CLAUDE.md — RouteException

Guidance for Claude Code when working in this repository.

## Project overview

RouteException is a B.Tech CSE (AIML) capstone project (problem statement #27). It is a multimodal AI assistant for last-mile delivery exceptions. It rebuilds a failed or disputed delivery from tracking data, delivery photos, driver voice notes and customer messages. It flags contradictions, picks a cause, suggests the next action, and drafts a neutral customer update. A dispatcher approves every update before the customer sees it.

**Core principle:** code decides facts and rules. The AI only reads unstructured inputs (audio, images, free text) and drafts text. A human approves every outgoing message.

### Users
- **Dispatcher:** reviews findings, edits and approves task cards and customer messages.
- **Driver:** marks deliveries live from a mobile web app (photo, GPS, status, optional voice note).
- **Customer:** sees approved updates (text + audio) and can raise a fraud report.

## Pipeline order

1. **Intake:** save files, create shipment row with status `processing`, return immediately.
2. **Extraction (AI):** Whisper transcript, vision JSON from photo, claims from customer text. Every extracted field keeps its source (file name + timestamp or line).
3. **Timeline (code):** merge all events, sort by time, tag each with source.
4. **Contradiction rules (code):** status vs customer, photo vs address, status vs driver note, time gap, missing evidence, GPS vs address (> 200 m, Haversine).
5. **Cause (AI):** exactly one of `address_issue`, `customer_unavailable`, `damaged`, `wrong_delivery`, `delayed`, with cited evidence. Low confidence → `needs_review`.
6. **Next action (code):** looked up in `config/rules.yaml`. Never generated by the LLM.
7. **Messages (AI + code):** draft task card and customer update, then run `guardrail.py`.
8. **Approval (human):** status `needs_review` → `approved`. Only then create audio and release to customer.

Shipment statuses: `processing` → `needs_review` → `approved` → `sent`.

## Hard rules (never break these)

The AI and the code must never:
- Blame the customer or the driver without evidence.
- Promise refunds or compensation.
- Show a driver's phone number or personal details to the customer.
- Show the customer anything the dispatcher has not approved.
- Let the LLM decide the next action or invent a cause outside the fixed taxonomy.
- Invent facts not present in the evidence.
- Email the police or accuse anyone automatically. Fraud reports give the customer an evidence pack, the 1930 helpline and a link to cybercrime.gov.in; the customer files the complaint.
- Show driver GPS to the customer.

`guardrail.py` must block refund/compensation words, phone-number patterns and blame phrases. Every new message type must pass through it. Add a test for every blocked pattern.

## Coding conventions

- Python 3.11+, type hints everywhere, format with `black`, lint with `ruff`.
- Keep routers thin: validation and calling services only. Logic lives in `app/services/`.
- Rule-based logic (timeline, rules, next action, guardrail) must be deterministic and fully unit-tested. The same input always gives the same output.
- All LLM calls go through one helper that requests JSON output, validates it with Pydantic, and retries once on invalid JSON.
- Cache LLM responses for demo cases so the demo works without API calls.
- Never hardcode API keys. Read them from `.env` via `config.py`.
- Log every approval, edit and fraud report to the audit log table.
- Business rules belong in `config/rules.yaml`, not in code.

## Data rules

- Synthetic data only. No real customer names, addresses, phone numbers or faces.
- Photos: doors and gates only, with printed fake gate numbers.
- Voice notes: recorded by the team.
- Never tune prompts or rules on `data/test_cases/`.

## Evaluation targets

| Metric | Target |
|---|---|
| Timeline completeness | ≥ 95% |
| Contradiction recall | ≥ 90% |
| Contradiction precision | ≥ 85% |
| Cause accuracy | ≥ 80% |
| Unsupported claims in customer messages | 0 |
| Guardrail violations in approved messages | 0 |
| GPS-mismatch detection | ≥ 90% |
| Evidence-pack completeness | 100% |

## Build priority

1. MVP first: intake → extraction → timeline → rules → cause → next action → messages → approval → TTS.
2. Then: live driver app, fraud report + evidence pack.
3. Later: Hindi/Punjabi audio, batch view, escalation deadlines, analytics, WhatsApp updates.

Do not start stretch features until the MVP passes the demo: a new shipment with a status/photo contradiction must be flagged, and the customer message must stay neutral.
